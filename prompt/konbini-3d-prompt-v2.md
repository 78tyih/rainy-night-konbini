## 0. 一句话说清它和普通提示词的区别

普通写法是**描述画面**：「帮我画一个赛博朋克风的便利店，要 3D 效果，要有雨」。
结果永远停在「看起来差不多」——因为画面能不能**做完**，不取决于描述得多细。

我们实际做下来，提示词要分三层，而且**第三层才是分水岭**：

| 层 | 回答的问题 | 缺了它会怎样 |
|---|---|---|
| 一 · 交付形态 | 这东西**是什么**？一张图、一段视频、还是一个能玩的东西？ | 得到一张好看的静帧，永远转不了 |
| 二 · 视觉语言 | 它**像不像**？三渲二 / 写实 / 卡通；色板、禁令 | 得到「AI 味」的塑料感 |
| 三 · 可验证性契约 | 它**能不能被做完**？命名、角色、闸门、探针、反例 | 停在 60 分，改一处坏一处，返工无穷 |

**绝大多数提示词只写了第一、二层。** 下面第三层，是我们从十几次评审里真正攒下来的东西。

**v2 新增第三层半**：可复现性。契约保证「测得准」，可复现性保证「测得的是同一个东西」。

## 1. 反向推导表：我们的实际动作 → 提示词条款

| 我们真做过的事 | 为什么非做不可（踩过的坑） | 对应条款 |
|---|---|---|
| 定死「单文件 HTML、无 UI、可轨道观察」 | 中途换过一次形态，前面全部作废 | 一 · ①②③④ |
| 用反向外壳做描边，而不是后期描边 | 后期描边在本项目尺度下粗细不匀 | 二 · ⑤ |
| 把落水管做成一整套（含接手） | 只插一根管子时，「接头」在模型里根本不存在 | 三 · ⑪ |
| 给每个构件起名 + 声明角色 | 报错信息里打的是名字；无名构件让三次事故溜过去 | 四 · ⑭ |
| 把构件按「可看穿 / 可停留」分两类 | **这一条被评审推翻了**——分类法本身会豁免掉「电线穿墙」这类问题 | 四 · ⑮ |
| 「有 role 没 name」直接判失败 | 把沉默的错当成风格问题 | 四 · ⑯ |
| 先建**闸门**，再跑探针 | 加载期一个错字，让所有探针**同时**变绿，而场景是空的 | 五 · ⑰ |
| 没有基线时必须说「本节没查」 | 曾经在没有基线时打印「一致」——那是编的 | 五 · ⑱ |
| 指纹改成**自动普查**构件族 | 手工清单只能看见已登记的族，新族静默溜过 | 五 · ⑲ |
| 探针开头做**页面错误硬失败** | 同上；一个坏构建能让所有测量都「通过」 | 六 · ㉑ |
| 「测到 0 个对象」判失败 | 「一个都没测到」和「全部合格」必须能区分 —— **但要留出合法空集合** | 六 · ㉑ |
| 量尺寸用几何自身包围盒 | 整树包围盒会把描边算进去，90 mm 的管量成 117 mm。**这个错犯了四次** | 六 · ㉑ |
| 阈值单独声明、不冒充来源值 | 拿验收阈值当图纸值，等于自己给自己发合格证 | 六 · ㉒ |
| 给探针加 `--file` 做**反例对照** | 没红过的探针只是装饰 | 七 · ㉓ |
| 反例必须真的跑 | 我自己的反例第一版**算错了**，结果「通过」，差点据此得出错误结论 | 七 · ㉔ |
| 绿灯但看着不对时，**先打射线**再改 | 四次「镜头/测量对准了错的东西」，每次都是射线解决的 | 八 · ㉕ |
| 数值的出处写进源码注释 | 我手抄跨距「0.770」而实测是「0.710」，被评审抓出来 | 九 · ㉙ |
| **复盘时发现：换台机器、换个目录，整套探针就跑不起来** | 硬编码浏览器路径、硬编码 URL、依赖页面全局变量 `scene` | 十 · ㉚～㉟ |

## 2. 提示词本体（完整版 · 可直接粘贴）

```text
你是一名三维场景构建者。请用一个单文件 HTML，交付一个可以自由旋转、缩放、
拖拽观看的微缩街景：雨夜的日式便利店街角。以第三视角观察，整体像一座微缩
三维模型 / 小型景观。

══════════ 一、交付形态（不可协商） ══════════
① 交付物是「一个」.html 文件，双击即开；不依赖构建工具、不依赖网络、
   不请求任何外部资源（字体、贴图、音频、CDN 一律内联）。
② 引擎用 three.js，**整段内联进产物**，让文件在断网时照常渲染。
   - 「内联 + 离线」是契约；**具体版本号是项目取值，不是契约**。
   - 注意：three.js 从 r150 起弃用 UMD 构建、r160 起移除
     （build/three.min.js 不再发布）。所以：
        · 若沿用全局变量写法 → 必须钉在 r160 之前的版本（本项目用 r128）；
        · 若用新版 → 改用 ES module + importmap 内联，不要指望 UMD。
     → 两种都行，但必须写明**你用了哪一种**，并保证断网可渲染。
③ 是「可轨道观察的微缩模型」：左键拖拽旋转、滚轮缩放、右键平移，带阻尼减速。
④ 没有任何 UI 界面元素——没有按钮、面板、标题、loading 条、水印。
   唯一允许的界面装饰是一个不接收指针事件的暗角遮罩。

══════════ 二、视觉语言（三渲二） ══════════
⑤ 渲染风格是「三渲二」，不是写实 PBR：
   - 材质用阶梯化 toon 材质，明暗交界是硬边，不是渐变；
   - 描边方案自选（本项目用「反向外壳描边」：同几何体微放大 + 背面渲染 + 深色，
     描边宽度按物体尺度分别设定，不全场景一个值）。
     ★ 描边是**可插拔的渲染实现**，不是场景实体的必备结构——
       后处理、法线外扩、节点材质都合法。
     谁对检查工具的要求是一样的：**能识别并排除「非语义的渲染辅助对象」**，
     测量只打在语义几何上。
⑥ 色板克制：低饱和的水泥灰 / 灰绿 / 暗蓝做环境，单一暖光源做焦点。
⑦ 禁令（这一条比你以为的重要）：
   ✗ 花哨渐变  ✗ 霓虹赛博  ✗ 极光  ✗ 动态背景  ✗ 高饱和撞色堆砌  ✗ 悬浮漂浮物
   ✗ 泛光到糊（bloom 只做极轻一层）
⑧ 夜雨的湿润感靠三件事，不靠发光：湿地面上的拖影反射、雨丝、水面涟漪与溅水。

   ※ ⑥⑦⑧ 是「本项目的美术方向」，属于示例配方。换场景可以整套换掉，
     但⑤的「描边必须可被检查器识别」是契约，不能换掉。

══════════ 三、场景清单（示例配方，可按项目增减） ══════════
⑨ 地面：一整块正方形底座，铺装分带（车行道 / 人行道 / 缘石 / 盲道）。
⑩ 主体建筑：24 小时便利店。玻璃幕墙、腰壁、袖壁、雨棚与檐板、店招。
⑪ 落水管系统（要成套，不要只插一根管子）：
   竪樋、抱箍、垫板、呼び樋、接手、斗颈、屋面落水口、雨水桝。
⑫ 城市物件：电线杆 + 电线 + 变压器、车辆、邻近建筑（形成巷子）。
⑬ 气候痕迹：泥はね帯（墙脚溅泥带）、泛水痕、积水、雨帘。

══════════ 四、构件声明契约（关键） ══════════
⑭ 命名范围这样划：**「会不会被问到」才是判据，不是「是不是 mesh」。**
   满足任意一条 → 必须有稳定名字（唯一、可读、带族前缀，例 SPOUT_BAND_front_3）：
     · 参与语义判断   · 参与尺寸测量   · 参与关系验证   · 出错时要被报告点名
   纯渲染辅助（描边壳、阴影代理、碰撞体、批量实例）**不要求实体级名字**，
   但必须能**追溯到所属实体**。
⑮ 声明字段要拆开——不要用两个大类包办一切。
   我们 v1 用「EXCLUDE（可看穿）/ SUPPORT（可停留）」二分，**评审推翻了它**，
   因为这两个词把五个不同的问题混成了一个。至少分成五个独立字段：
     · 它是什么            （decal / wire / pipe / wall / ground / fitting …）
     · 有没有体积
     · 会不会遮挡视线
     · 能不能当支撑面
     · 参与哪条探针
   ⚠ 反例就在本项目里：电线我们归成了「零体积、可看穿」，但它**有体积**、
     **会遮挡**，而且「线穿过杆」「线穿墙」正是「几何碰上 ≠ 语义关系成立」
     的高发区。二分法会把这类问题**从分类法层面豁免掉**。
⑯ 两条纪律：
   - 「有 role 却没有 name」= 交付失败，不是风格问题。
   - **警惕自证循环**：模型给自己写 role 是「声明」，声明只负责**找到对象**；
     它「真的支撑了建筑」必须**另测**，不能因为声明了就认定成立。

══════════ 五、自检闸门（先问「值不值得测」） ══════════
⑰ 在跑任何测量之前，先跑一个闸门，只回答一个问题：
   「这次构建值不值得测？」
   闸门至少检查：
   - 加载期是否抛错（抛错 = 场景不完整 = 后面所有数字作废）
   - 可能参与测量 / 判断 / 报错的构件是否都有名字
   - 关键构件族的「数量指纹」是否落在允许范围内
   - 场景里到底出现了哪些构件族（自动普查，不是手工维护的清单）
⑱ 闸门必须：
   - 支持重建基线（--update），且重建时逐条打印差异，不静默吞掉
   - 在没有基线时明确报「本节未做比对」，而不是打印「一致」
   - 把「这个构建不成立」和「这个构建跟上次不一样」**分成两类**，
     前者不允许被 --update 覆盖
   - 更新基线前必须有人看过画面 —— 否则「无脑 --update」会变成一条
     比手工维护清单更危险的静默失效通道
⑲ 构件族数量**不要求与基线完全相等**。合理迭代（增删一个配件、合并几何）
   不该被逼着回滚。支持三种约束：
     · 必须存在   · 最小 / 最大数量   · 与已批准基线的差异需显式登记
   报告要区分「失败」和「需要人工确认的基线变化」。
⑳ 新增构件族必须能被自动发现。手工列表只能看见已经登记过的族，
   而「我忘了登记」正是它溜过去的方式。
   ★ 但自动普查**看不见「彻底删掉且没留记录」的族**——
     所以「实际对象普查」和「需求侧应存在的清单」是两份，必须互相核对。

══════════ 六、度量探针（出数字，不出图） ══════════
㉑ 每个探针只回答「一个问题」，打印实测值与断言值，用「通过/失败」收尾。
   允许共享一次场景加载、允许附带诊断字段（对象名、命中距离、路径），
   附带信息**不计入 PASS 条件**。
㉒ 四条硬规矩：
   - 探针开头做「页面错误硬失败」：加载抛错直接判 FAIL 并终止。
   - 空集合要分两种，别一刀切：
       · 要求存在的目标测到 0 个 → FAIL；
       · 已声明「允许为空」的目标 → 可以 PASS，
         但必须**先用一个已知存在的对象跑通同一条查询**，
         证明「查询本身没坏」，否则空结果可能只是探针瞎了。
   - 测尺寸前，先声明**测的是什么物理量、在哪个坐标系里测**：
       · 量几何本体 → 用 geometry.boundingBox（先 computeBoundingBox）
       · 量世界占位 → Box3.setFromObject 也可以，但要**先过滤描边壳**
     「整树包围盒会把描边算进去」是坑；「某个 API 天生不可用」是错的说法。
   - 阈值 / 容差必须标明它是「来源值」还是「验收阈值」，不得混为一谈。
     拿验收阈值冒充来源值，等于自己给自己发合格证。

══════════ 七、反例对照（没红过的探针不可信） ══════════
㉓ 每个探针都要能指向另一个构建产物（--file）。
   把构建「故意改坏」——删一个构件、挪 50 mm、把 A 换成 B——
   确认探针会红，而且**是因为预期的原因红**。
   ★ 如果反例只是让页面加载崩了，它什么都没验证到——
     反例必须能走到目标断言，并以预期理由失败。
㉔ 反例必须真的跑，不能靠推理。我自己的第一版反例就算错了，
   结果反例「通过」，差点据此得出错误结论。

══════════ 八、返工纪律（最重要的一条） ══════════
㉕ 当测量结果与预期不符时：
   ✗ 不许放宽阈值 / 容差让它变绿
   ✗ 不许删掉旁边的构件让断言满足
   ✗ 不许把「几何碰上了」当成「语义关系成立」
   ✓ 回到源码，补上缺失的那个零件，或改正那个错误的表达式
   若出现「绿灯但看着还是不对」：
     · 先打射线，查清挡在前面的是谁 → 这只能解决**遮挡**类问题；
     · 比例失调 / 光照不对 / 材质语义错，射线**查不出来**，
       要靠截图与人工视觉核验。三条证据链不能互相顶替。

══════════ 九、验收标准 ══════════
㉖ 单文件、离线可开、无 UI、可自由轨道观察、帧率稳定。
㉗ 可能被问到 / 被测到的构件都有 name 与 role 声明。
㉘ 闸门 PASS；核心探针全绿；每个反例对照都各自会红，且红在预期的断言上。
㉙ 每个关键尺寸在源码注释里能追溯到出处，并标明是
   [来源值] / [项目取值] / [几何推导] / [未验证] 中的哪一类。
   ★ 所有快照数字（本项目的 993 网格 / 407 描边壳 / 36 配件）必须标注
     「这是基线示例，不是标准值」——否则半年后它会从经验退化成教条。

══════════ 十、可复现与可测（少了这节，前面都白搭） ══════════
㉚ **资源闭包**：断网打开必须照常渲染；不请求任何外部资源；
   声明文件大小与首屏可交互时间的目标上限。
㉛ **WebGL 不可用时必须显式失败并说明原因**，不能白屏、不能静默降级。
㉜ **坐标系与单位写死**：本项目 1 单位 = 1 米、Y 轴向上、
   地面顶面为 y=0。所有断言用同一套坐标。
㉝ **透明度 / 深度排序 / 阴影 / 实例化的规则要写明**：
   哪些构件走透明混合、哪些实例化、哪些投影。没有统一规则，
   场景遍历会产出一堆假阳性。
㉞ **随机效果固定 seed**：雨丝、涟漪、散布物一律走固定种子，
   否则每次加载画面不同，「改前 / 改后」根本没法对比。
㉟ **可测性桥**：如果场景写在闭包或模块里，外部探针拿不到它。
   约定暴露一个诊断接口，例如：
       window.__SCENE_DIAGNOSTICS__ = {
         getScene: () => scene,
         getCamera: () => camera,
         getRenderer: () => renderer
       };
   拿不到就显式判「不可测」，**不能把不可测当成通过**。
   ★ 另外：断言和截图必须用**同一个构建产物**，
     否则会出现「测的是 A，展示的是 B」。
```

## 3. 精简版（发给别人用 / 贴在推文里）

```text
用一个单文件 HTML 做雨夜便利店街角的微缩 3D 场景（three.js 整段内联，
断网可开，无 UI，可自由旋转缩放拖拽）。风格三渲二：阶梯 toon 材质 +
描边（反向外壳或后处理都行），低饱和灰绿/水泥灰配单一暖光源；
禁止霓虹、渐变、极光、动态背景。

然后按这个顺序自检，不要跳步：
1) 命名范围 =「会不会被问到」：参与判断/测量/关系核验/出错点名的构件，
   必须有稳定名字。纯渲染辅助（描边壳等）不要求命名，但必须能追溯到所属实体。
   声明字段拆开写：它是什么 / 有没有体积 / 会不会遮挡 / 能不能当支撑 / 参与哪条探针。
   —— 别用两个大类包办，那会豁免掉「电线穿墙」这类问题。
2) 先写一个闸门，回答「这次构建值不值得测」：加载有没有抛错、有没有该命名
   却没名字的构件、构件族数量是否落在允许范围内。加载抛错时，后面所有测量作废。
3) 再写探针，每个只回答一个问题，出数字不出图。
   空集合分两种：要求存在的测到 0 个 = 失败；声明允许为空的可以过，
   但必须先用一个已知存在的对象证明查询没坏。
4) 量尺寸前先说清测的是什么、在哪个坐标系：量几何本体用 geometry.boundingBox；
   量世界占位可以用 setFromObject，但要先过滤描边壳。
5) 把构建故意改坏，确认探针会红，而且红在预期的断言上——
   只是让页面崩掉，不等于验证到了东西。

可复现：断网可渲染、WebGL 不可用要显式报错、随机效果固定 seed、

断言与截图用同一个产物。

返工时：不许放宽阈值让它变绿，不许删掉旁边的构件让断言满足。

```

## 4. 诚实的分工说明（写推文时要用到）

这套提示词**分成两半，对模型能力的要求完全不同**：

- **第一、二、三层中的「描述」部分**（①～⑬）：任何能写代码的模型都能执行，
  区别只是审美。给一段好描述 + 三渲二 + 色板禁令，就能得到「像样的第一版」。
- **第三层中的「契约」部分**（⑭～㉟）：要求模型**能跑代码、能改自己的代码、
  能读自己的测量结果**。纯聊天模型做不到——它没法把构建改坏再验证探针会不会红。

所以教学时要把话说清楚：

| 你手上是什么 | 能拿到什么 | 提示词怎么给 |
|---|---|---|
| 纯聊天模型 | 一版静态代码，好看但改不动 | 给 ①～⑬，拿到代码自己跑 |
| 能跑代码的 Agent | 能迭代到收敛的完整项目 | 全文给，重点是 ⑭～㉟ |

**这也是这篇文章真正的论点**：让 AI 做出这种画面，瓶颈从来不是「描述得够不够细」，
而是「你有没有给它一套能自我证伪的流程」。上面 ⑭～㉟ 每一条，对应我们实际
摔过的一个跟头。

**另外一句要说实话的**：这套东西目前**不太可移植**。探针硬编码了浏览器路径、
硬编码了产物 URL、依赖页面全局变量 `scene` —— 换台机器、换个目录就要改代码。
上面 ㉟ 那条「可测性桥」就是为解决这个才加进来的。
