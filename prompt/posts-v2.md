## 推文一 · 讲方法

**惊呆了，我们用 DeepSeek V4.1-Flash 生成了《雨夜便利店细节迷道》，像走进去能购买关东煮。有什么特点？**

先说清楚它是什么：不是一个视频，也不是一张渲染图。

它是一个**单文件 HTML**——双击就开，不需要联网、不需要装东西。能自由旋转、缩放、拖拽，像捧着一个微缩模型在手里转。

**特点一：它是三渲二，不是写实。**
明暗交界是**硬边**，不是渐变；每一个实体外面还挂了一层反向描边——整个场景 **407 个描边壳**。所以它看起来像动画，不像照片。这个选择有个副作用：它没法靠"糊"来假装真实，形体对不对，一眼就看得见。

**特点二：细节是按"成套"做的，不是按"好看"做的。**
比如一根落水管，我们做了 **36 个配件**：管身、四道抱箍、每道抱箍外面一块垫板、底部外扩的呼水嘴、上端的接手、穿板的斗颈、屋面落水口、地面的雨水桝。管底离地 **10 毫米**，正好落进格栅里。
再比如两棵电线杆，拆成 **84 个零件**，拉出去 **31 根线**。
这些数字不是拿来炫的——真东西之所以真，是因为它有**接缝**。

**特点三：没有任何 UI。**
没有按钮、没有面板、没有标题、没有水印。整块屏幕上只有场景本身，加一个不接收点击的暗角。

**然后是这篇文章真正想说的。**

同样一句「帮我画一个 3D 的便利店」，为什么大多数人做不出来？

因为写提示词的时候，我们只写了两层：**要什么形态**、**要什么风格**。
而决定它能不能**做完**的，是第三层：**可验证性契约**。

翻成人话就是——不要只告诉 AI 画什么，还要告诉它**怎么检查自己画错了**：

- **给"会被问到的东西"起名字**。判据不是「它是不是一个 mesh」，而是「它会不会参与判断、会不会被测量、出错时要不要被点名」。会，就必须有稳定名字。因为报错信息里打的就是名字，而「(无名) BoxGeometry」正是让错误溜过去的措辞。
- 光有一个名字不够，**还要把它拆开描述**：它是什么、有没有体积、会不会挡住视线、能不能当支撑面。我们一开始只分「可看穿 / 可停留」两类，结果电线被归进"零体积可看穿"——可它会挡，而且"线穿过杆"恰恰是最容易出问题的地方。**用两个大类包办，等于主动豁免掉一整类错误。**
- 先跑一个**闸门**，只回答一个问题：这次构建值不值得测？我们踩过的最深的坑是——加载时一个错字，让**所有**检查同时变绿，而场景其实是空的。
- 量尺寸要先说清**在量什么**。用整树包围盒会把描边外壳算进去，**90 毫米的管子被量成 117 毫米**。这个错我们犯了四次。（所以问题不是"某个函数天生不能用"，而是"你没说清量的是几何本体还是世界占位"。）
- 每个检查都要**故意把构建改坏**再验一遍。没红过的检查，只是装饰——而且有个讲究：如果只是让页面崩掉，那不叫验证，得让它**死在预期的那条断言上**。
- 最后，**让它可复现**：断网能开、WebGL 挂了要报错而不是白屏、雨丝涟漪用固定随机种子、把场景对象暴露一个能取到的接口。不然"改前改后"根本没得比。

一句话：**让 AI 做出这种画面，瓶颈从来不是「描述得够不够细」，而是「你有没有给它一套能自我证伪的流程」。**

它长什么样、我们做了什么、提示词全文——见下一条。

## 推文二 · 讲细节（结尾附提示词）

**那家雨夜便利店，我们到底做了多少东西？**

（配图：hero 全景 + 落水口特写 + 电线杆特写）

把它转起来，第一眼看到的是**雨**。
不是一层滤镜——雨丝、地面上的涟漪、雨点砸在积水上的溅水，三样是分开做的。

**墙脚有泥点。**
四面墙的墙脚都有一条 **300 毫米**高的溅泥带，还有顺墙流下来的泛水痕。这一条是后来才补的：早先只有正面和右面有，转到左墙一看，光溜溜的，一眼假。

**落水管做的是一整套。**
不是插一根管子。管身 φ90；中间四道抱箍，箍带内径留 4 毫米公差；每道抱箍外面还有一块 30×40 的**垫板**——真正打进墙里的是那块垫板，不是管子。
管子往下收成一个外扩的**呼水嘴**，把水甩离墙面；往上，管顶**不伸到雨棚面以上**，而是在雨棚板下面先接进一个「**接手**」，再往上穿过 160 毫米厚的雨棚板，接上屋面落水口。管底离地 10 毫米，落进一个 320 见方的**雨水桝**。

**雨棚下面还有一层。**
160 毫米的结构板之外，底下还挂着一层 50 毫米的吊顶装饰板。
而幕墙玻璃一直做到顶——**整栋楼在 0.45 米到 2.30 米之间全是玻璃，没有墙**。所以后来我们在前后两个转角补了「袖壁」，否则那两道抱箍根本找不到东西固定。

**再转过去，是一整条巷子。**
主墙外面半米就是邻楼的立面。两棵电线杆立在路边，杆上有横担、绝缘子、抱箍、接线盒、变压器；拉出去的电线粗细不一。

**店里是亮的，玻璃也几乎是透的**（透明度设到 0.04）。
货架、后面的冷柜、收银台、门口的自动售货机、玻璃上贴的海报和贴纸，都做得出来。

**下面是生成它的提示词。**

```text
用一个单文件 HTML 做雨夜便利店街角的微缩 3D 场景（three.js 整段内联，
断网可开，无 UI，可自由旋转缩放拖拽）。风格三渲二：阶梯 toon 材质 +
描边（反向外壳或后处理都行），低饱和灰绿/水泥灰配单一暖光源；
禁止霓虹、渐变、极光、动态背景。

然后按这个顺序自检，不要跳步：
1) 命名范围 =「会不会被问到」：参与判断/测量/关系核验/出错点名的构件，
   必须有稳定名字。纯渲染辅助（描边壳等）不要求命名，但必须能追溯到所属实体。
   声明字段拆开写：它是什么 / 有没有体积 / 会不会遮挡 / 能不能当支撑 / 参与哪条探针。
   —— 别用两个大类包办，那会豁免掉「电线穿墙」这类问题。
2) 先写一个闸门，回答「这次构建值不值得测」：加载有没有抛错、有没有该命名
   却没名字的构件、构件族数量是否落在允许范围内。加载抛错时，后面所有测量作废。
3) 再写探针，每个只回答一个问题，出数字不出图。
   空集合分两种：要求存在的测到 0 个 = 失败；声明允许为空的可以过，
   但必须先用一个已知存在的对象证明查询没坏。
4) 量尺寸前先说清测的是什么、在哪个坐标系：量几何本体用 geometry.boundingBox；
   量世界占位可以用 setFromObject，但要先过滤描边壳。
5) 把构建故意改坏，确认探针会红，而且红在预期的断言上——
   只是让页面崩掉，不等于验证到了东西。

可复现：断网可渲染、WebGL 不可用要显式报错、随机效果固定 seed、
坐标系与单位写死、故意暴露一个取 scene/camera 的诊断接口，
断言与截图用同一个产物。

返工时：不许放宽阈值让它变绿，不许删掉旁边的构件让断言满足。
发现「绿灯但看着不对」，先打射线查清挡在前面的是什么——
但射线只查遮挡，比例和光照问题它查不出来。
```

## 附：两个数字的出处（防止被问住）

| 文中数字 | 来源 |
|---|---|
| 993 网格 / 407 描边壳 / 192 有名构件 | 场景普查（`scene.traverse` 计数）· **本项目基线示例，非标准值** |

| 抱箍内径差 4 毫米、垫板 30×40 | `src/04_store.js` downspout 段注释 |
| 檐高 2.62 / 雨棚 160 / 吊顶板 50 毫米 | `EAVE_Y = 2.62`，0104 段注释 |
| 玻璃 0.45–2.30 全透段 | `GZ0 = 0.45`、`GZ1 = 2.30` |
| 玻璃透明度 0.04 | `GLASSM` 定义 |
