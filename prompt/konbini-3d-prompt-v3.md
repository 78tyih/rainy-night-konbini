# 雨夜便利店 3D 街角 · 反向推导提示词 v3

> v2 → v3 的唯一动因：**v2 只有"契约"，没有"规格"。**
> 别人拿 v2 能做出一个**能自我检查**的场景，但做不出**同一类场景**——
> 因为灯怎么打、店怎么排、颗粒度堆到什么程度，全都没写。
> v3 把这一层补上，并且**每个数字都带出处**（见 §5）。
>
> 保留：v2 的 35 条契约（可验证性），一条没删。
> 新增：第二层「设计规格」——渲染与相机 / 灯光体系 / 便利店主体 / 地面铺装 /
> 气候与湿润感 / 城市物件 / 贴图颗粒度，共 7 节、约 90 项实测参数。
>
> v1、v2 保留不删。源项目：单文件 HTML + three.js，可自由旋转/缩放的雨夜
> 日式便利店街角微缩模型，三渲二，无 UI。

## 0. 一句话说清它和普通提示词的区别

普通写法是**描述画面**：「帮我画一个赛博朋克风的便利店，要 3D 效果，要有雨」。
结果永远停在「看起来差不多」——因为画面能不能**做完**，不取决于描述得多细。

我们实际做下来，提示词要分三层，而且**后两层才是分水岭**：

| 层 | 回答的问题 | 缺了它会怎样 | 对应节 |
|---|---|---|---|
| 一 · 交付形态 | 这东西**是什么**？ | 得到一张好看的静帧，永远转不了 | §2-一 |
| 二 · 设计规格 | 它**像不像**？尺寸、灯位、颗粒度 | 得到「AI 味」的塑料感；或者像了但立不住 | §2-二~九 |
| 三 · 可验证性契约 | 它**能不能被做完**？ | 停在 60 分，改一处坏一处，返工无穷 | §2-十~十六 |

**绝大多数提示词只写了第一层。** 第二层靠"看得多"能补，
第三层只能靠摔跟头——下面每一节都对应我们实际摔过的一次。

**关于数字怎么用（重要，别跳过）**：下文带 ▸ 的值是本项目的**实测取值**，
它们的意思是「这样做能 work」，不是「必须这么做」。
换场景应当重新推导，但**同类关系不能变**——
比如「玻璃带要占立面大部分高度」「画面最亮的人造物必须是店面而不是地面」
「痕迹要按类型分别做，不能糊一次贴图」——这几条是设计判断，不是参数。

## 1. 反向推导表：我们的实际动作 → 提示词条款

| 我们真做过的事 | 为什么非做不可（踩过的坑） | 对应条款 |
|---|---|---|
| 定死「单文件 HTML、无 UI、可轨道观察」 | 中途换过一次形态，前面全部作废 | 一 · ①②③④ |
| 相机 fov 压到 32 度 | 广角把微缩感拍成了实景 | 二 · ⑤ |
| 灯光全部用**实体光源**，不做 bloom | 泛光会把三渲二的硬边糊掉 | 三 · ⑬ |
| 把「画里最亮的人造物是店面」写成硬约束 | 檐外灯调猛了，地面比橱窗亮，视线被地面抓走 | 三 · ⑲ |
| 店内灯排成**两排各三盏** | 单排会被货架端头挡住，三块端头亮度差超过 15% | 三 · ⑱ |
| 立面的玻璃带占 65% 高度 | 腰壁做高了，从 20° 俯角看，每厘米腰壁吃掉 2.7 厘米室内 | 五 · ㉔ |
| 雨棚做成**双层**（结构板 + 吊顶板） | 单层板从下面看是"一块白板"，没有纵深 | 五 · ㉗ |
| 落水管做成一整套（含接手） | 只插一根管子时，「接头」在模型里根本不存在 | 五 · ㉚ |
| 雨用 ribbon 而不是 line | GL 线宽被后端钳到 1 设备像素，DPR2 下等于看不见 | 七 · ㊱ |
| 涟漪用 `r = r0 + c·t^(2/3)` 扩张 | 线性扩张看着像动画，不像水面 | 七 · ㊳ |
| 痕迹**按类型分开做**（泥/泛水/檐滴/水洼/落叶） | 想用一张万能贴图糊过去，结果是"脏得均匀"，一眼假 | 七 · ㊷ |
| 贴图全部程序化 canvas 生成 | 外部贴图 = 联网 = 单文件契约破了 | 九 · ㊾ |
| 给每一个构件起名 + 声明角色 | 报错信息里打的是名字；无名构件让三次事故溜过去 | 十 · ㊿ |
| 把构件按「可看穿 / 可停留」分两类 | **这一条被评审推翻了**——分类法本身会豁免掉「电线穿墙」这类问题 | 十 · 51 |
| 先建**闸门**，再跑探针 | 加载期一个错字，让所有探针**同时**变绿，而场景是空的 | 十一 · 53 |
| 指纹改成**自动普查**构件族 | 手工清单只能看见已登记的族，新族静默溜过 | 十一 · 56 |
| 量尺寸用几何自身包围盒 | 整树包围盒会把描边算进去，90 mm 的管量成 117 mm。**这个错犯了四次** | 十二 · 58 |
| 给探针加 `--file` 做**反例对照** | 没红过的探针只是装饰 | 十三 · 60 |
| 绿灯但看着不对时，**先打射线**再改 | 四次「镜头/测量对准了错的东西」，每次都是射线解决的 | 十四 · 62 |
| 复盘时发现：换台机器、换个目录，整套探针跑不起来 | 硬编码浏览器路径、硬编码 URL、依赖页面全局变量 | 十六 · 71 |

## 2. 提示词本体（完整版 · 可直接粘贴）

```text
你是一名三维场景构建者。请用一个单文件 HTML，交付一个可以自由旋转、缩放、
拖拽观看的微缩街景：雨夜的日式便利店街角。以第三视角观察，整体像一座微缩
三维模型 / 小型景观。

★ 下文带 ▸ 的值是本项目的实测取值。它们的意思是「这样做能 work」，
  不是「必须照抄」。换场景应重新推导，但**同类关系不能变**：
  · 玻璃带要占立面大部分高度
  · 画里最亮的人造物必须是店面，不能是地面
  · 痕迹要按类型分别做，不能糊一张贴图了事
  这三条是设计判断，不是参数。

══════════ 一、交付形态（不可协商） ══════════
① 交付物是「一个」.html 文件，双击即开；不依赖构建工具、不依赖网络、
   不请求任何外部资源（字体、贴图、音频、CDN 一律内联）。
② 引擎用 three.js，**整段内联进产物**，让文件在断网时照常渲染。
   - 「内联 + 离线」是契约；**具体版本号是项目取值，不是契约**。
   - three.js 从 r150 起弃用 UMD 构建、r160 起移除。若沿用全局变量写法，
     必须钉在 r160 之前的版本（本项目 ▸ r128）；若用新版，
     改用 ES module + importmap 内联。两种都行，但必须写明用了哪一种。
③ 是「可轨道观察的微缩模型」：左键拖拽旋转、滚轮缩放、右键平移，带阻尼减速。
④ 没有任何 UI 界面元素——没有按钮、面板、标题、loading 条、水印。
   唯一允许的界面装饰是一个不接收指针事件的暗角遮罩。

══════════ 二、渲染与相机 ══════════
⑤ 相机用透视但**窄视角**，不是广角：
   ▸ fov 32°、near 0.5、far 300
   ▸ 初始机位 az 0.86 / el 0.22 / dist 27.0，看向 (-0.2, 1.35, -0.5)
   ▸ 开自动旋转，但用户一拖就停
   广角会把微缩感拍成实景——**微缩感的第一来源是视角，不是尺寸**。
⑥ 渲染器：
   ▸ antialias true、powerPreference 'high-performance'
   ▸ devicePixelRatio 上限钳到 2（不钳，笔记本 3x 屏会直接掉帧）
   ▸ outputEncoding = sRGBEncoding
   ▸ shadowMap 开，类型 PCFSoftShadowMap
   ▸ clearColor 0x090c17
⑦ **不用后期处理**。不要 toneMapping、不要 bloom、不要 EffectComposer。
   三渲二的硬边和明确的明暗交界是这套画面成立的基础，泛光一上就糊。
   ★ 这条是硬约束，与⑬「灯靠实体光源」是一套。
⑧ 天空是一个 90 m 半径的开口圆柱穹顶（BackSide、不写深度、不吃雾），
   顶点着色器按高度做三段渐变 + 一条地平光晕：
   ▸ 低 vec3(0.075, 0.098, 0.176) / 中 (0.055, 0.070, 0.130) / 高 (0.030, 0.040, 0.078)
   ▸ 过渡 smoothstep(0.0, 0.42, h) 与 smoothstep(0.40, 1.0, h)
   ▸ 地平光晕 pow(max(0, 1-|h-0.30|*5.5), 2.0) × vec3(0.055, 0.045, 0.030)
   要点：**天空是"画"出来的，不是一盏灯打出来的**，所以它不会污染下面的
   明暗关系。

══════════ 三、灯光体系（这一节最容易被做错） ══════════
⑨ 冷光打底，四层，全部很弱：
   ▸ 环境光    0x2e3a5e @ 0.22
   ▸ 半球光    天 0x54699c / 地 0x191e2c @ 0.18
   ▸ 主光      0xa8c2ff @ 0.30，位于 (-16, 22, -12)，
               **唯一投影光源**，shadow map 2048²，
               正交范围 ±17、near 1 far 70、bias -0.0009、normalBias 0.02
   ▸ 轮廓光    0x6f8cc9 @ 0.10，位于 (13, 7, 15)
   四层加起来只有 0.80——**夜不是靠压暗做出来的，是靠"亮的东西很少"**。
⑩ 暖光**只有一处焦点**：店外唯一暖色实体光源是一盏檐外灯
   ▸ 0xffc98a @ 0.72，distance 10、decay 1.2，位置 (-0.6, 2.05, 4.0)
   它的职责是把光洒在门口人行道上，制造「店在营业」的入口感。
⑪ 店内暖光用**实体点光源**，不是自发光贴图：
   ▸ 颜色 0xffd7a2、强度 0.80、distance 9、decay 1.35、安装高度 y = 2.20
   ★ 注意：**不用 bloom、不用 emissive 加成**。灯亮是因为它真的照亮了
     货架和商品，不是因为它自己发光。这是三渲二的画法。
⑫ 店内天花板另有一层自发光：天花板贴图 emissive 0xffd6a0，强度 1.15，
   下面配 13 条灯槽（每条 ▸ 2.2 × 0.09 × 0.36，y = 2.555）
   与一层半透明发光盘（▸ 3.0 × 1.1，opacity 0.30，y = 2.46）。
   自发光只负责"天花板自己是亮的"，不负责照亮别的东西。
⑬ 招牌的发光靠 **Sprite 光晕**（AdditiveBlending + 径向渐变贴图），
   不靠 bloom：
   ▸ 招牌光晕 0xffe7bd，4 个；悬挑竖招光晕 0xffe0b0，1 个
   ▸ 光晕带极轻微的随机抖动（amp 0.12），模拟老旧灯管
⑭ 先按"哪盏灯照哪件事"把灯全部摆出来，然后再**删**，最后总量要落到个位数：
   ▸ 本项目先摆 15 盏静态点光源：6（店内）+ 4（自贩机）+ 1（巷内壁灯）
     + 2（路灯）+ 1（公告板）+ 1（檐外）
   ▸ 再删掉 6 盏（自贩机 4 + 巷灯 + 公告板），实留 **9 盏**
   为什么删：夜戏里灯一多，画面就失去"暗的主体"，而且每盏灯都是性能成本。
   删的标准是——**这盏灯有没有在承担一件具体的叙事职责**。
   （先多后删，和"一开始就少摆"不一样：不摆出来，
     你不会知道哪盏其实是多余的。）

   ── 排布规则（比参数重要）──
⑮ 灯的位置要按**"哪一面会被看到"**来排，不是按"每货架一盏"平均分配。
⑯ 店内灯排成**两排各三盏**：
   ▸ 前排 z = 2.05、后排 z = -1.30；每排 x = -5.0 / -3.0 / -1.0
   ▸ 高度 2.20（在货架体之上，不被遮挡）
   为什么不能只排一排：单排在测试里被货架端头挡住，
   三块端头亮度差超过 15%，看起来像有两个店。
⑰ 灯要照亮**路人实际会看到的那一面**：
   ▸ 前排 z=2.05 在每块端头前 0.35 m，照的是街道看到的那张脸
   ▸ 后排 z=-1.30 照的是长边商品面
⑱ **最亮的人造物必须是店面。** 这一条要当验收标准用。
   ▸ 实测：檐外灯曾经提到 1.2，结果人行道亮度 157、
     水洼亮度 174，都超过了玻璃带自身均值 130
     → 观众的视线被地面抓走，不是被商品抓走
     → 压回 0.72
   雨夜的地面应该是**亮部的配菜**，不该比橱窗更亮。

══════════ 四、视觉语言（三渲二） ══════════
⑲ 渲染风格是「三渲二」，不是写实 PBR：
   - 材质用阶梯化 toon 材质，明暗交界是**硬边**，不是渐变
     （本项目▸ 用一个 N 级灰色渐变贴图当 gradientMap）
   - 描边方案自选（本项目用「反向外壳描边」：同几何体微放大 + 背面渲染 +
     深色，描边宽度按物体尺度分别设定，不全场景一个值）
     ★ 描边是**可插拔的渲染实现**，不是场景实体的必备结构——
       后处理、法线外扩、节点材质都合法。
     谁对检查工具的要求是一样的：**能识别并排除「非语义的渲染辅助对象」**，
     测量只打在语义几何上。
⑳ 色板克制：低饱和的水泥灰 / 灰绿 / 暗蓝做环境，暖色只出现在店里和灯下。
   ▸ 本项目品牌三色 0x3ea173（绿）/ 0xf2a83c（橙）/ 0xe0503c（红），
     只用在招牌、色带、自贩机面板上——**全局其他地方不许出现这三个色**。
㉑ 禁令（这一条比你以为的重要）：
   ✗ 花哨渐变  ✗ 霓虹赛博  ✗ 极光  ✗ 动态背景  ✗ 高饱和撞色堆砌  ✗ 悬浮漂浮物
   ✗ 泛光到糊（本项目直接不用 bloom）
㉒ 夜雨的湿润感靠三件事，不靠发光：
   湿地面上的拖影反射、雨丝、水面涟漪与溅水（详见第七节）。
   ※ 第二~四节是「本项目的美术方向」，属于示例配方，换场景可整套换掉。

══════════ 五、便利店主体（怎么把它"排"出来） ══════════
㉓ 先定体量，再切角：
   ▸ 店面 10.0 m（X）× 9.2 m（Z），前右 45° 切掉 3.0 m 做入口
   ▸ 整块场地基座 23.2 m 见方，基座顶面 -0.08，人行道顶面 0.00，路面顶面 -0.04
   ▸ 主墙体厚 0.30
   要点：**体量要"小"，但细节要"密"**。微缩感来自比例，
   不来自把东西做小——10 m 的店配 0.3 m 的墙，和真建筑是同一个比例。

   ── 立面是"一层层叠"出来的，不是一块墙贴图 ──
㉔ 立面从下往上分六层，**每一层都有自己的标高和厚度**：
   ▸ ① 腰壁      0.14 → 0.45   （厚 0.30，混凝土色）
   ▸ ② 玻璃带    0.45 → 2.30   （厚 0.04 的玻璃 + 0.15 竖梃）
   ▸ ③ 上冒头    2.30 → 2.44   （厚 0.26，铝色）
   ▸ ④ 品牌色带  2.46 起三条，每条高 0.04，厚 0.28（绿/橙/红）
   ▸ ⑤ 上部盒体  2.62 → 4.05   （厚 0.30）
   ▸ ⑥ 屋顶板    4.05 → 4.27（厚 0.22）+ 压顶带 4.27 → 4.67（厚 0.16）
   ★ **玻璃带占立面总高的 65%**。这一条不能妥协：
     腰壁做高了，从 20° 俯角看，每厘米腰壁会吃掉约 2.7 厘米室内可见面积。
   玻璃材质：toon 材质 + 颜色 0xc3d8e6 + **透明度 0.04** + depthWrite false。
   透明度要压到极低——玻璃是"几乎全透"的，不是"半透的雾"。
㉕ 袖壁（翼墙）是补出来的，不是一开始就有的：
   玻璃一直做到顶时，抱箍找不到东西固定。所以在前后两个转角补
   ▸ 从 0.45 到 2.62、厚 0.30 的翼墙，边缘再加 0.06 厚的见切り
   凡是"玻璃通到顶"的立面，都要问一句：**挂在墙上的东西挂在哪**。
㉖ 雨棚挑出 1.125 m，并且是**双层**：
   ▸ 结构板 2.62 → 2.78（厚 0.16）
   ▸ 吊顶装饰板 2.57 → 2.62（厚 0.05，比结构板内缩一点）
   ▸ 前端鼻隠し（檐板）2.34 → 2.78，厚 0.09
   为什么必须双层：单层板从雨棚下面往上看是一块白板，没有纵深；
   双层之间那道阴影线才是"构造感"的来源。
㉗ 招牌分四块，位置标高都不同：
   ▸ 店面上三块平板 3.9 / 3.2 / 2.1 × 0.975，置于 y = 3.42
   ▸ 屋顶上一块盒体 2.6 × 1.25 × 0.16
   ▸ 前左一根悬挑竖招 0.16 × 1.5 × 0.9，出挑到人行道上方
   招牌文字用 canvas 画（见第九节），**不要用系统字体直接渲染**——
   后者在不同机器上会长得不一样。
㉘ 门开在 45° 切角上：
   ▸ 门扇玻璃 2.30 高，滑开距离 0.86，配「自動ドア」贴条与门口地垫
   ▸ 门把手是一张 0.22 高的贴纸，不是几何体
㉙ 店内必须能"从外面看见商品"，所以室内要真做：
   ▸ 三组货架 x = -5.0 / -3.0 / -1.0，高 1.35、深 0.86，
     端头再加 0.88 × 1.30 × 0.30 的端头柜（三层）
   ▸ 冷柜一组（柜体 5.9 宽 × 2.25 高 × 0.8 深，三个门）
   ▸ 收银台 3.2 × 0.95 × 0.8 + 收银机 + 咖啡机
   ▸ 关东煮台 0.9 × 1.0 × 1.5
   ▸ ATM 0.85 × 1.7 × 0.6（贴墙，旋转 90°）
   ▸ 橱窗低展台（x -6.30..-4.55，高 0.98，深 0.42）
   ▸ 天花板 2.60 高，配 13 条灯槽
   ▸ 海报 7 张（店内墙 4 + 玻璃内侧 3）
   关键：**玻璃几乎全透，所以室内每一件都会被看到**。
   室内做得敷衍，外面一眼就露。
㉚ 落水管（竪樋）必须做成**一整套**，不能只插一根管子：
   ▸ 管身 φ90、长 2.59 m、管底离地 10 mm
   ▸ 四道抱箍，箍带内径留 4 mm 公差
   ▸ 每道抱箍外面一块 30 × 40 的垫板——**真正打进墙里的是垫板，不是管子**
   ▸ 底端外扩的呼び樋（把水甩离墙面）
   ▸ 上端：管顶**不伸到雨棚面以上**，先在板下接进一个「接手」，
     再穿过 160 mm 厚的雨棚板，接屋面落水口
   ▸ 地面收进一个 320 见方的雨水桝
   这一整套 ▸ 36 个配件。
   ★ **「成套」是这套画面最重要的方法论**：
     真东西之所以真，是因为它有**接缝**。一个物件该有几个接头、
     几个紧固件、几个过渡件，一个都不能省——省掉的那个，
     恰恰是视觉上最"不对"的那个。

══════════ 六、地面与铺装 ══════════
㉛ 地面分**两层标高**，不要一层平面走到底：
   ▸ 基座顶面（结构层，看不见）        -0.08
   ▸ 路面顶面（边缘压条顶面，真正看到的）-0.04
   ▸ 人行道板顶面                      0.00（板厚 0.08）
   为什么：路和人是不同高度，压条那道 40 mm 的侧边就是"路缘"。
   本项目曾经**所有路面特征都埋在地下 40 mm**（因为都按基座顶面写），
   是靠向下打射线一层层量出来的。
㉜ 铺装分带要完整：
   ▸ 车行道（深灰蓝 + 油渍）、人行道（砖缝 + 高光缝）、缘石（压边条）、
     盲道（点字ブロック，4 块 0.30 × 0.30，间距 0.30）、角部铺装
   ▸ 标线：斑马线前路 9 条 / 右路 8 条、停止线、中心线、停车位线、编号方块
   ▸ 排水沟两条（前 12.0 长 / 右 10.6 长，宽 0.34），沟内有水线
㉝ 干湿分带是一条**独立的一层**，不是靠整体调暗：
   ▸ 用一张 multiply 混色贴图，边界用三条正弦摆动做出不规则边缘
   ▸ 前人行道 12.4 × 2.50、右人行道 10.4 × 2.10
   雨后的地面是"有的地方湿、有的地方干"，不是均匀一层水。

══════════ 七、气候与湿润感（颗粒度的主战场） ══════════
㉞ 雨要"看得见"，靠的是**单条的对比度**，不是数量：
   ▸ 2130 条，每条是 6 顶点的 ribbon（**不是 GL line**——
     GL 线宽被后端钳到 1 设备像素，DPR2 下等于看不见）
   ▸ 单条长 0.14–0.26 m、宽约 1.5 CSS px、透明度 0.28、颜色 0xcde0ff
   ▸ 按终速分层 6/7/8/9 m/s，落雨空间顶 17 m、跨度 22 m
   ▸ 风速向量 (0.95, 0.30)，每米下落横向漂移 0.16
   ★ 数量与宽度是**恒定墨量互相换算**的：想加宽就必须减数量，
     否则天空覆盖率会突破上限，画面变"白茫茫"。
㉟ 雨必须被**遮挡物截断**，而且要用解析盒体求交，不能只判中心点：
   ▸ 5 组遮挡盒：店铺体量、前雨棚、右雨棚、邻楼、一个空槽位
   ▸ 每条雨丝对自己的落点求最高顶盖，头尾分别截断
   ▸ 地面截断高度取路面顶面
   只判中心点会出现"雨棚上方没雨、棚下却有雨"的穿帮。
㊱ 涟漪是一套**实例化参数系统**，不是逐点动画：
   ▸ 512 个槽位、接受率 220 次/秒
   ▸ 初始半径 0.004，扩张按 r = r0 + c·t^(2/3)，c = 0.106
     （**不是线性**——线性扩张看着像动画，不像水面）
   ▸ 环带半宽 0.009（全带宽约 18 mm）、双色 0x66799a / 0x171c26
   ▸ 冲击核半径 0.018、核心色 0xa9bcda
   ▸ 生成规则：半径/时长/峰值按 pow(random, 2.2) 偏置；
     深水处 ×1.9、浅水 ×1.35；檐滴落点再 ×1.5；
     大涟漪有 35% 概率补一圈延迟的第二环
   亮点在于**深度感知**：涟漪落在已建水洼里时会变大、变久——
   这比"每滴雨画一个圈"高级得多。
㊲ 溅水不是一个粒子系统，而是**落水事件直接生成涟漪**：
   ▸ 1400 颗 CPU 雨滴做环境雨，落地且未被遮挡才发射
   ▸ 檐滴走真实重力 9.81，落地阈值在人行道面上方 60 mm，
     横向受风偏移，下落时纵向拉伸（最多 2.4 倍）
   ▸ 檐滴站点 10 处（前檐 6 + 右檐 4），水珠用 0.055 半径的小球
   （旧版做过 700 个 additive 粒子，因为点尺寸被钳到 1 px 而删掉）
㊳ 湿地面反射用**反射卡 + 湿痕池**两层，都是 additive 拖影：
   ▸ 主反射卡两张：0xffc98a（宽 8.5、长 7.0、op 0.40）、
     0xffe0b0（宽 4.0、长 4.5、op 0.34）
   ▸ 店内每一盏暖灯配一张小反射卡（宽 2.2、长 4.4、op 0.20）
   ▸ 反射卡随相机朝向做偏航，永远对着镜头（这是"拖影"而不是"倒影"）
   ▸ 湿痕池 6 处：暖色三处 0xffe0b4、冷色三处 0xbfe0f2
   ▸ 路灯下再补一块 1.70 × 1.70 的圆光斑（op 0.20）
㊴ 有风，而且是**低频噪声驱动**的，不是固定值：
   ▸ 基值 (0.95, 0.30)，四个频段 (tau, amp) =
     (0.30, 0.10) (1.50, 0.16) (6.00, 0.11) (20.0, 0.07)
   ▸ 雨、檐滴横偏、涟漪落点、所有被风吹的东西**共用同一个风向量**
   共用是重点：各算各的风，雨往东飘、水花往西溅，一眼假。
㊵ **痕迹要按类型分开做，不能糊一张贴图了事**：
   ▸ 泥はね帯（墙脚溅泥）——**几何**，不是贴图：
     高 0.30、厚 0.012、底边距地 0.17，四面墙各一条，角色标 grime
   ▸ 泛水痕（雨水冲刷）——几何：宽 30–70 mm、长 300–1020 mm，
     **只出现在奇数分缝处**（全出现就变成"斑马"，不像自然冲刷）
   ▸ 檐板滴水痕——4 处，宽 32 mm、长 100–240 mm，从檐板下沿往下
   ▸ 水洼 12 处，尺寸随机 ±15%，透明度 0.6–0.9
   ▸ 落叶 9 处、路面补丁 3 块、井盖 1 个
   ★ 判断标准：**这些痕迹各自有各自的原因和位置规律**。
     "脏得均匀"是 AIGC 味最重的表现之一。

══════════ 八、城市物件（画面不能只有一个店） ══════════
㊶ 电线杆是画面里**零件最多**的东西，值得单独做：
   ▸ 2 根，高 8.6 / 8.2 m，位置在路两侧
   ▸ 杆身本体 φ280 起、根卷、三层横担（高压 / 低压 / 通信）
   ▸ 零件族：横担、绝缘子、抱箍、垫板、接线盒、变压器、引下线、号牌
   ▸ 实测 ▸ 84 个零件
㊷ 电线用**抛物线悬链**，不是直线：
   ▸ 高压垂度 0.25 / 0.28 / 0.30，低压 0.24 / 0.26，通信线 0.34 / 0.46
   ▸ 用 TubeGeometry（32 段径向 / 8 边）保证有体积
   ▸ 出场地边界处要做截断并加封头
   ▸ 实测 ▸ 23 根
   线必须**有垂度**——拉直的电线是"线框模型"，不是电线。
㊸ 周边物件按"每类 ≥ 1"铺开，别只摆一个：自贩机 4 台、停靠轿车 1 辆、
   自行车 2 辆、路灯 2 盏、信号灯 1 座、垃圾桶、伞架、邮筒、路锥、
   护栏 2 段、公告板、路牌、停车场牌、邻楼 1 栋（3.0 × 7.4 × 11.2，
   与主墙隔出半米宽的巷子）、后场（空调外机、栈板、铁丝网）。
㊹ 邻楼的作用是**形成巷子**——它给了整个场景一个"进深"，
   也让主墙的侧立面有理由被看到。没有它，场景是个孤岛。

══════════ 九、贴图与颗粒度 ══════════
㊺ **所有贴图都用 canvas 程序化生成**，不引入任何外部图片。
   这既是单文件契约的要求，也顺带保证了"没有一处是照片感"。
㊻ 贴图分辨率按"它有多大"定，不是一律 512：
   ▸ 大面积铺装 512×512（路面 / 人行道砖 / 地砖 / 天花，带 repeat）
   ▸ 混凝土 256×256
   ▸ 招牌 1024×256、竖招 256×768、短招 512×256
   ▸ 自贩机面板 384×640、ATM 面板 256×384
   ▸ 货架正面 512×256、海报 384×512
   ▸ 杆身 48×512（细长件用非方形）
   ▸ 光晕 / 阴影 / 环 / 烟雾 都是 128×128
㊼ 贴图的画法要点：
   ▸ 路面：底色 + 两轮噪点 + 二十几个浅色椭圆当油渍
   ▸ 人行道：砖底 + 分格线 + 一条高光缝（**缝要亮**，不然不像新砖）
   ▸ 水洼：5 个重叠软形状 + 平滑随机游走轮廓 + 断续边缘高光 + 暖光拖影
   ▸ 干湿分带：白=不起作用，湿色做 multiply，边界三条正弦摆动
   ▸ 反射拖影：竖直渐变，再用 destination-out 把两侧压黑，留中间亮条
   ▸ 杆身："溅水污染"竖直渐变 + 二十几条流水痕 + 底部九十粒砂
㊽ 招牌 / 海报 / 价目卡上的文字要用 canvas 画出来，
   中日文都要有（本项目用一组日文系统字体栈兜底），
   **不要指望字体渲染一致**——它是贴图，不是文本。
㊾ 颗粒度的判断标准不是"物件数"，是**"每一类都有多个，且每一个都不一样"**：
   同一个东西重复摆十次，看起来比摆两次还假。
   本项目最终 ▸ 993 个实体网格 + 407 个描边壳、192 个有名构件。

══════════ 十、构件声明契约 ══════════
㊿ 命名范围这样划：**「会不会被问到」才是判据，不是「是不是 mesh」。**
   满足任意一条 → 必须有稳定名字（唯一、可读、带族前缀，例 SPOUT_BAND_front_3）：
     · 参与语义判断   · 参与尺寸测量   · 参与关系验证   · 出错时要被报告点名
   纯渲染辅助（描边壳、阴影代理、碰撞体、批量实例）**不要求实体级名字**，
   但必须能**追溯到所属实体**。
51 声明字段要拆开——不要用两个大类包办一切。
   我们最初用「EXCLUDE（可看穿）/ SUPPORT（可停留）」二分，**已被推翻**，
   因为这两个词把五个不同的问题混成了一个。至少分成五个独立字段：
     · 它是什么            （decal / wire / pipe / wall / ground / fitting …）
     · 有没有体积
     · 会不会遮挡视线
     · 能不能当支撑面
     · 参与哪条探针
   ⚠ 反例就在本项目里：电线我们归成了「零体积、可看穿」，但它**有体积**、
     **会遮挡**，而且「线穿过杆」「线穿墙」正是「几何碰上 ≠ 语义关系成立」
     的高发区。二分法会把这类问题**从分类法层面豁免掉**。
52 两条纪律：
   - 「有 role 却没有 name」= 交付失败，不是风格问题。
   - **警惕自证循环**：模型给自己写 role 是「声明」，声明只负责**找到对象**；
     它「真的支撑了建筑」必须**另测**，不能因为声明了就认定成立。

══════════ 十一、自检闸门（先问「值不值得测」） ══════════
53 在跑任何测量之前，先跑一个闸门，只回答一个问题：
   「这次构建值不值得测？」
   闸门至少检查：
   - 加载期是否抛错（抛错 = 场景不完整 = 后面所有数字作废）
   - 可能参与测量 / 判断 / 报错的构件是否都有名字
   - 关键构件族的「数量指纹」是否落在允许范围内
   - 场景里到底出现了哪些构件族（自动普查，不是手工维护的清单）
54 闸门必须：
   - 支持重建基线（--update），且重建时逐条打印差异，不静默吞掉
   - 在没有基线时明确报「本节未做比对」，而不是打印「一致」
   - 把「这个构建不成立」和「这个构建跟上次不一样」**分成两类**，
     前者不允许被 --update 覆盖
   - 更新基线前必须有人看过画面 —— 否则「无脑 --update」会变成一条
     比手工维护清单更危险的静默失效通道
55 构件族数量**不要求与基线完全相等**。合理迭代（增删一个配件、合并几何）
   不该被逼着回滚。支持三种约束：
     · 必须存在   · 最小 / 最大数量   · 与已批准基线的差异需显式登记
   报告要区分「失败」和「需要人工确认的基线变化」。
56 新增构件族必须能被自动发现。手工列表只能看见已经登记过的族，
   而「我忘了登记」正是它溜过去的方式。
   ★ 但自动普查**看不见「彻底删掉且没留记录」的族**——
     所以「实际对象普查」和「需求侧应存在的清单」是两份，必须互相核对。

══════════ 十二、度量探针（出数字，不出图） ══════════
57 每个探针只回答「一个问题」，打印实测值与断言值，用「通过/失败」收尾。
   允许共享一次场景加载、允许附带诊断字段（对象名、命中距离、路径），
   附带信息**不计入 PASS 条件**。
58 四条硬规矩：
   - 探针开头做「页面错误硬失败」：加载抛错直接判 FAIL 并终止。
   - 空集合要分两种，别一刀切：
       · 要求存在的目标测到 0 个 → FAIL；
       · 已声明「允许为空」的目标 → 可以 PASS，
         但必须**先用一个已知存在的对象跑通同一条查询**，
         证明「查询本身没坏」，否则空结果可能只是探针瞎了。
   - 测尺寸前，先声明**测的是什么物理量、在哪个坐标系里测**：
       · 量几何本体 → 用 geometry.boundingBox（先 computeBoundingBox）
       · 量世界占位 → Box3.setFromObject 也可以，但要**先过滤描边壳**
     「整树包围盒会把描边算进去」是坑；「某个 API 天生不可用」是错的说法。
   - 阈值 / 容差必须标明它是「来源值」还是「验收阈值」，不得混为一谈。
     拿验收阈值冒充来源值，等于自己给自己发合格证。

══════════ 十三、反例对照（没红过的探针不可信） ══════════
59 每个探针都要能指向另一个构建产物（--file）。
   把构建「故意改坏」——删一个构件、挪 50 mm、把 A 换成 B——
   确认探针会红，而且**是因为预期的原因红**。
   ★ 如果反例只是让页面加载崩了，它什么都没验证到——
     反例必须能走到目标断言，并以预期理由失败。
60 反例必须真的跑，不能靠推理。我自己的第一版反例就算错了，
   结果反例「通过」，差点据此得出错误结论。

══════════ 十四、返工纪律（最重要的一条） ══════════
61 当测量结果与预期不符时：
   ✗ 不许放宽阈值 / 容差让它变绿
   ✗ 不许删掉旁边的构件让断言满足
   ✗ 不许把「几何碰上了」当成「语义关系成立」
   ✓ 回到源码，补上缺失的那个零件，或改正那个错误的表达式
   本项目最典型的一次：闸门报红，第一反应是「断言写严了」，
   查下来是**接手根本没做**——补上零件，不是放宽断言。
62 若出现「绿灯但看着还是不对」：
   · 先打射线，查清挡在前面的是谁 → 这只能解决**遮挡**类问题；
   · 比例失调 / 光照不对 / 材质语义错，射线**查不出来**，
     要靠截图与人工视觉核验。三条证据链不能互相顶替。
   （本项目共四次「镜头/测量对准了错的东西」，每一次都是射线解决的。）

══════════ 十五、验收标准 ══════════
63 单文件、离线可开、无 UI、可自由轨道观察、帧率稳定。
64 可能被问到 / 被测到的构件都有 name 与 role 声明。
65 **最亮的人造物是店面**（可用截图测亮度验证）。← 第⑱条的落地
66 闸门 PASS；核心探针全绿；每个反例对照都各自会红，且红在预期的断言上。
67 每个关键尺寸在源码注释里能追溯到出处，并标明是
   [来源值] / [项目取值] / [几何推导] / [未验证] 中的哪一类。
   ★ 所有快照数字（993 网格 / 407 描边壳 / 36 配件 / 84 零件）必须标注
     「这是基线示例，不是标准值」——否则半年后它会从经验退化成教条。

══════════ 十六、可复现与可测（少了这节，前面都白搭） ══════════
68 **资源闭包**：断网打开必须照常渲染；不请求任何外部资源；
   声明文件大小与首屏可交互时间的目标上限。
69 **WebGL 不可用时必须显式失败并说明原因**，不能白屏、不能静默降级。
70 **坐标系与单位写死**：本项目 1 单位 = 1 米、Y 轴向上、地面顶面为 y=0。
   所有断言用同一套坐标。
71 **透明度 / 深度排序 / 阴影 / 实例化的规则要写明**：
   哪些构件走透明混合、哪些实例化、哪些投影。没有统一规则，
   场景遍历会产出一堆假阳性。
72 **随机效果固定 seed**：雨丝、涟漪、散布物一律走固定种子
   （本项目 ▸ 种子 20261007，LCG 递推），
   否则每次加载画面不同，「改前 / 改后」根本没法对比。
   ★ 但要注意：本项目仍有部分效果用 Math.random()，
     所以**只保证"冻结后不动"，不保证"跨运行可复现"**——
     任何基于跨运行对比的结论都必须写明这一点。
73 **可测性桥**：如果场景写在闭包或模块里，外部探针拿不到它。
   约定暴露一个诊断接口，例如：
       window.__SCENE_DIAGNOSTICS__ = {
         getScene: () => scene, getCamera: () => camera, getRenderer: () => renderer
       };
   拿不到就显式判「不可测」，**不能把不可测当成通过**。
   ★ 另外：断言和截图必须用**同一个构建产物**，
     否则会出现「测的是 A，展示的是 B」。
```

## 4. 诚实的分工说明（写推文时要用到）

这套提示词**分成两半，对模型能力的要求完全不同**：

- **第一、二层的「描述」部分**（①～㊾）：任何能写代码的模型都能执行，
  区别只是执行得准不准。给足规格 + 三渲二 + 灯位 + 颗粒度，就能得到
  「像样的第一版」。
- **第三层的「契约」部分**（㊿～73）：要求模型**能跑代码、能改自己的代码、
  能读自己的测量结果**。纯聊天模型做不到——它没法把构建改坏再验证探针会不会红。

| 你手上是什么 | 能拿到什么 | 提示词怎么给 |
|---|---|---|
| 纯聊天模型 | 一版静态代码，好看但改不动 | 给 ①～㊾，拿到代码自己跑 |
| 能跑代码的 Agent | 能迭代到收敛的完整项目 | 全文给，重点是 ㊿～73 |

**这篇文章真正的论点**：让 AI 做出这种画面，瓶颈从来不是「描述得够不够细」，
而是**两件事**——你有没有给它足够具体的**规格**（否则像但不对），
以及有没有给它一套**能自我证伪的流程**（否则改一处坏一处）。
第二层对应前者，第三层对应后者。

**另外要说实话的两点**：
- 这套东西目前**可移植性只到"工具层"**：探针里仍写死了本项目的构件前缀
  与验收阈值，换个项目要改这些，但运行环境（浏览器 / 路径 / 场景取用）
  已经解耦，换机器换目录都能跑。
- 本项目仍有部分效果用 `Math.random()`，**冻结能保证"不动"，
  但不保证"跨运行可复现"**。任何基于跨运行对比的结论都要标注这一点。
