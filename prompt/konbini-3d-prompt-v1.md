# 雨夜便利店 3D 街角 · 反向推导提示词 v1

> 从「我们实际怎么把它做出来的」反推出提示词，而不是从「我想看到什么」正着写。
> 源项目：单文件 HTML + three.js，可自由旋转/缩放的雨夜日式便利店街角微缩模型，三渲二，无 UI。
> 用途：推文 + 教学 + 后续凝练成 skill。

---

## 0. 一句话说清它和普通提示词的区别

普通写法是**描述画面**：「帮我画一个赛博朋克风的便利店，要 3D 效果，要有雨」。
结果永远停在「看起来差不多」——因为画面能不能**做完**，不取决于描述得多细。

我们实际做下来，提示词要分三层，而且**第三层才是分水岭**：

| 层 | 回答的问题 | 缺了它会怎样 |
|---|---|---|
| 一 · 交付形态 | 这东西**是什么**？一张图、一段视频、还是一个能玩的东西？ | 得到一张好看的静帧，永远转不了 |
| 二 · 视觉语言 | 它**像不像**？三渲二 / 写实 / 卡通；色板、禁令 | 得到「AI 味」的塑料感 |
| 三 · 可验证性契约 | 它**能不能被做完**？命名、角色、闸门、探针、反例 | 停在 60 分，改一处坏一处，返工无穷 |

**绝大多数提示词只写了第一、二层。** 下面第三层，是我们从十几次评审里真正攒下来的东西。

## 1. 反向推导表：我们的实际动作 → 提示词条款

| 我们真做过的事 | 为什么非做不可（踩过的坑） | 对应条款 |
|---|---|---|
| 定死「单文件 HTML、无 UI、可轨道观察」 | 中途换过一次形态，前面全部作废 | 一 · ①②③④ |
| 用反向外壳做描边，而不是后期描边 | 后期描边在本项目尺度下粗细不匀 | 二 · ⑤ |
| 把落水管做成一整套（含接手） | 只插一根管子时，「接头」在模型里根本不存在 | 三 · ⑪ |
| 给**每一个**构件起名 + 声明角色 | 报错信息里打的是名字；无名构件让三次事故溜过去 | 四 · ⑭ |
| 把角色分「可看穿」和「可停留」两类 | 零体积的贴花被当成结构支撑面，报了一堆假红 | 四 · ⑮ |
| 「有 role 没 name」直接判失败 | 把沉默的错当成风格问题 | 四 · ⑯ |
| 先建**闸门**，再跑探针 | 加载期一个错字，让所有探针**同时**变绿，而场景是空的 | 五 · ⑰ |
| 没有基线时必须说「本节没查」 | 曾经在没有基线时打印「一致」——那是编的 | 五 · ⑱ |
| 指纹改成**自动普查**构件族 | 手工清单只能看见已登记的族，新族静默溜过 | 五 · ⑲ |
| 探针开头做**页面错误硬失败** | 同上；一个坏构建能让所有测量都「通过」 | 六 · ㉑ |
| 「测到 0 个对象」判失败而非通过 | 「一个都没测到」和「全部合格」必须能区分 | 六 · ㉑ |
| 量尺寸用几何自身包围盒 | 整树包围盒会把描边算进去，90 mm 的管量成 117 mm。**这个错犯了四次** | 六 · ㉑ |
| 阈值单独声明、不冒充来源值 | 拿验收阈值当图纸值，等于自己给自己发合格证 | 六 · ㉒ |
| 给探针加 `--file` 做**反例对照** | 没红过的探针只是装饰 | 七 · ㉓ |
| 反例必须真的跑 | 我自己的反例第一版**算错了**，结果「通过」，差点据此得出错误结论 | 七 · ㉔ |
| 绿灯但看着不对时，**先打射线**再改 | 四次「镜头/测量对准了错的东西」，每次都是射线解决的 | 八 · ㉕ |
| 数值的出处写进源码注释 | 我手抄跨距「0.770」而实测是「0.710」，被评审抓出来 | 九 · ㉙ |

## 2. 提示词本体（完整版 · 可直接粘贴）

```text
你是一名三维场景构建者。请用一个单文件 HTML，交付一个可以自由旋转、缩放、
拖拽观看的微缩街景：雨夜的日式便利店街角。以第三视角观察，整体像一座微缩
三维模型 / 小型景观。

══════════ 一、交付形态（不可协商） ══════════
① 交付物是「一个」.html 文件，双击即开；不依赖构建工具、不依赖网络。
② 引擎用 three.js（r128 UMD 版本整段内联进 <script>，不要 CDN 引用）。
③ 是「可轨道观察的微缩模型」：左键拖拽旋转、滚轮缩放、右键平移，带阻尼减速。
④ 没有任何 UI 界面元素——没有按钮、面板、标题、loading 条、水印。
   唯一允许的界面装饰是一个不接收指针事件的暗角遮罩。

══════════ 二、视觉语言（三渲二） ══════════
⑤ 渲染风格是「三渲二」，不是写实 PBR：
   - 材质用阶梯化 toon 材质，明暗交界是硬边，不是渐变；
   - 每个可见实体挂一层「反向外壳描边」（同几何体微放大 + 背面渲染 + 深色），
     描边宽度按物体尺度分别设定，不要全场景一个值。
⑥ 色板克制：低饱和的水泥灰 / 灰绿 / 暗蓝做环境，单一暖光源做焦点。
⑦ 禁令（这一条比你以为的重要）：
   ✗ 花哨渐变  ✗ 霓虹赛博  ✗ 极光  ✗ 动态背景  ✗ 高饱和撞色堆砌  ✗ 悬浮漂浮物
   ✗ 泛光到糊（bloom 只做极轻一层）
⑧ 夜雨的湿润感靠三件事，不靠发光：湿地面上的拖影反射、雨丝、水面涟漪与溅水。

══════════ 三、场景清单 ══════════
⑨ 地面：一整块正方形底座，铺装分带（车行道 / 人行道 / 缘石 / 盲道）。
⑩ 主体建筑：24 小时便利店。玻璃幕墙、腰壁、袖壁、雨棚与檐板、店招。
⑪ 落水管系统（要成套，不要只插一根管子）：
   竪樋、抱箍、垫板、呼び樋、接手、斗颈、屋面落水口、雨水桝。
⑫ 城市物件：电线杆 + 电线 + 变压器、车辆、邻近建筑（形成巷子）。
⑬ 气候痕迹：泥はね帯（墙脚溅泥带）、泛水痕、积水、雨帘。

══════════ 四、构件声明契约（关键） ══════════
⑭ 每一个 mesh 必须带两样东西：
   - name：唯一、可读、带族前缀（例：SPOUT_BAND_front_3）
   - userData.role：它是「什么」（结构关系），而不是它「长什么样」
⑮ 角色分两类，必须分开：
   - EXCLUDE（零体积的视觉覆盖层：贴花 / 污渍 / 电线 / 反光片）
     → 检查工具必须「看穿」它；它不需要名字。
   - SUPPORT（有体积、可能被当成支撑面）
     → 必须有名字。因为出问题时报告里打的就是名字，
       「(无名) BoxGeometry」正是让事故溜过去的措辞。
⑯ 「有 role 却没有 name」视为交付失败，不是风格问题。

══════════ 五、自检闸门（先问"值不值得测"） ══════════
⑰ 在跑任何测量之前，先跑一个闸门，只回答一个问题：
   「这次构建值不值得测？」
   闸门至少检查：
   - 加载期是否抛错（抛错 = 场景不完整 = 后面所有数字作废）
   - 所有 SUPPORT 角色是否都有名字
   - 关键构件族的「数量指纹」是否与基线一致
   - 场景里到底出现了哪些构件族（自动普查，不是手工维护的清单）
⑱ 闸门必须：
   - 支持重建基线（--update），且重建时逐条打印差异，不静默吞掉
   - 在没有基线时明确报「本节未做比对」，而不是打印「一致」
   - 把「这个构建不成立」和「这个构建跟上次不一样」分成两类，
     前者不允许被 --update 覆盖
⑲ 新增构件族必须能被自动发现。手工列表只能看见已经登记过的族，
   而「我忘了登记」正是它溜过去的方式。

══════════ 六、度量探针（出数字，不出图） ══════════
⑳ 每个探针只回答「一个问题」，打印实测值与断言值，用「通过/失败」收尾。
㉑ 三条硬规矩：
   - 探针开头做「页面错误硬失败」：加载抛错直接判 FAIL 并终止。
   - 「测到 0 个对象」= FAIL，不是 PASS。一个都没测到与全部合格必须能区分。
   - 测距离 / 接触 / 搭接时，用「几何自身的包围盒」；
     绝不用 Box3.setFromObject —— 它会把描边外壳算进去。
㉒ 断言值必须标明它是「来源值」还是「验收阈值」，不得混为一谈。
   拿验收阈值冒充来源值，等于自己给自己发合格证。

══════════ 七、反例对照（没红过的探针不可信） ══════════
㉓ 每个探针都要能指向另一个构建产物（--file）。
   把构建「故意改坏」——删一个构件、挪 50 mm、把 A 换成 B——
   确认探针会红，而且是因为预期的原因红。
   一个从没被看见失败过的断言只是装饰。
㉔ 反例必须真的跑，不能靠推理。我自己的第一版反例就算错了，
   结果反例「通过」，差点据此得出错误结论。

══════════ 八、返工纪律（最重要的一条） ══════════
㉕ 当测量结果与预期不符时：
   ✗ 不许放宽阈值 / 容差让它变绿
   ✗ 不许删掉旁边的构件让断言满足
   ✗ 不许把「几何碰上了」当成「语义关系成立」
   ✓ 回到源码，补上缺失的那个零件，或改正那个错误的表达式
   若出现「绿灯但看着还是不对」，以几何为准、以图为线索；
   先打射线查清挡在前面的是谁，再改，不要靠肉眼调参重试。

══════════ 九、验收标准 ══════════
㉖ 单文件、离线可开、无 UI、可自由轨道观察、帧率稳定。
㉗ 所有 SUPPORT 构件都有 name 与 role。
㉘ 闸门 PASS；核心探针全绿；每个反例对照都各自会红。
㉙ 每个关键尺寸在源码注释里能追溯到出处，并标明是
   [来源值] / [项目取值] / [几何推导] / [未验证] 中的哪一类。
```

## 3. 精简版（发给别人用 / 贴在推文里）

```text
用一个单文件 HTML 做雨夜便利店街角的微缩 3D 场景（three.js，无 UI，
可自由旋转缩放）。风格三渲二：阶梯 toon 材质 + 反向外壳描边，低饱和色板
配单一暖光源；禁止霓虹、渐变、极光、动态背景。

然后按这个顺序自检，不要跳步：
1) 给每个构件起名并声明角色；零体积的贴花/污渍/电线归类为「可看穿」，
   有体积的构件归类为「可停留」——后者必须有名字。
2) 先写一个闸门，回答「这次构建值不值得测」：加载有没有抛错、有没有无名构件、
   构件族数量与上一次是否一致。加载抛错时，后面所有测量作废。
3) 再写探针，每个只回答一个问题，出数字不出图。
   「测到 0 个对象」要判失败，不是通过。
4) 量尺寸用几何自身的包围盒，不要用会把描边外壳算进去的整树包围盒。
5) 把构建故意改坏，确认探针会红——没红过的断言只是装饰。

返工时：不许放宽阈值让它变绿，不许删掉旁边的构件让断言满足。
发现「绿灯但看着不对」，先打射线查清挡在前面的是什么，再改。
```

## 4. 诚实的分工说明（写推文时要用到）

这套提示词**分成两半，对模型能力的要求完全不同**：

- **第一、二、三层中的「描述」部分**（①～⑬）：任何能写代码的模型都能执行，
  区别只是审美。给一段好描述 + 三渲二 + 色板禁令，就能得到「像样的第一版」。
- **第三层中的「契约」部分**（⑭～㉙）：要求模型**能跑代码、能改自己的代码、
  能读自己的测量结果**。纯聊天模型做不到——它没法把构建改坏再验证探针会不会红。

所以教学时要把话说清楚：

| 你手上是什么 | 能拿到什么 | 提示词怎么给 |
|---|---|---|
| 纯聊天模型 | 一版静态代码，好看但改不动 | 给 ①～⑬，拿到代码自己跑 |
| 能跑代码的 Agent | 能迭代到收敛的完整项目 | 全文给，重点是 ⑭～㉙ |

**这也是这篇文章真正的论点**：让 AI 做出这种画面，瓶颈从来不是「描述得够不够细」，
而是「你有没有给它一套能自我证伪的流程」。上面 ⑭～㉙ 每一条，对应我们实际
摔过的一个跟头。
